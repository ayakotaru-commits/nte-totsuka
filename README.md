# TOTSUKA（個人用・戸塚駅周辺 3D 散策）

横浜市戸塚区・戸塚駅周辺を OpenStreetMap のデータから 3D で再現し、キャラクターで歩き回れるブラウザゲーム。

## 起動

`start.bat` をダブルクリック → ブラウザで http://localhost:8000/ が開く（Python が必要）。

### スマホ・タブレット（タッチ操作）

タッチ専用の端末で開くと、自動でタッチ操作になる（`public/src/touch.js`）。PC で試すときは URL に `?touch`。

| 操作 | 動作 |
|---|---|
| 画面の左側をドラッグ | 移動（触れた所にスティックが出る。浅く倒すと歩き、深く倒すと走り） |
| 画面の右側をドラッグ | 視点 |
| 2 本指でつまむ | ズーム |
| ジャンプ / ダッシュ | ジャンプ（2段）/ 押している間ダッシュ |
| 地図（ミニマップのタップでも可） | 大きいマップ（ドラッグで移動・つまんで拡大縮小・タップで行き先・「ワープ」で移動） |
| 時間 / 戻る / 写真 | 時間帯 / スタート地点に戻る / ストリートビュー |

修正モード（E）と GLB 書き出し（G）は PC 専用。タッチ操作のときは軽くするため、解像度の倍率の上限を 1.5、影の解像度を半分にしている。
iPhone はタブが使えるメモリが少なく、超えるとページごと落ちる（「このページを開けません」）。そのためタッチ操作のときは `public/src/lowmem.js` でメモリを節約している:
頂点データの JS 側の控えを GPU に送った後に手放す、看板などの模様を半分の解像度で作って描画用のメモリを手放す、キャラ（VRM）の 2048 px の模様を 1024 px に縮める、地面の法線と色を小さい型で持つ。
重いときは URL に `?noshadow`（影なし）・`?pr=1`（解像度を下げる）・`?noaa`、フレームレートを画面に出すには `?perf`。

### スマホから開く（GitHub Pages）

`main` に入るたびに、`public/` が GitHub Pages に自動で公開される（`.github/workflows/pages.yml`）。
URL は `https://ayakotaru-commits.github.io/nte-totsuka/`。初回だけ、リポジトリの Settings → Pages → Source を「GitHub Actions」にする。
公開されるのはゲームの表示だけで、修正モードの保存（`tools/server.py` の API）は使えない。

### 光と空気感（public/src/look.js）
街のデータには手を入れず、描き方だけで質感を上げる。5,600 棟すべてに自動で効く。
- 空の映り込み: 空のシェーダ（太陽の円盤は消す）をぼかして `scene.environment` に入れる。時間帯が変わると作り直す。強くすると日陰が明るくなって影が消えるので、弱め（昼 `envI` 0.1）にし、半球ライトを 8 割に下げて合わせている
- かすみ: 霧を距離に応じて指数的に濃くする（80 m 先から。250 m で約 11%・600 m で約 29%）。`THREE.ShaderChunk.fog_fragment` を差し替える
- 物の陰（AO）: three.js の GTAO を半分の解像度で。法線は深度から復元するので、街を 2 回描かない
- にじみ（ブルーム）: 夜の窓・看板・街灯が光ってにじむ。昼は弱い
- 色の仕上げ: 露出 → ACES → 彩度・コントラスト（sRGB で掛ける）・周辺減光
- 時間帯ごとの強さは `time.js` の `envI`・`hemiK`・`ao`・`bloom`・`bloomT`・`sat`。URL で上書きできる（`?envI=0.2&aoK=0.8`）
- スマホ・タブレットは映り込みとかすみだけ（AO・にじみ・色の仕上げは画面の大きさの描画先を何枚も使うのでメモリを食う）。`?post` で使える
- 切り分け: `?plain`（全部なし = 以前の見え方）、`?noao`、`?nobloom`、`?noenv`。撮影は `node tools/dev/shot.js <出力> <視点> --q '&plain'` で以前の見え方

### 座標系（Unity 移行時も共通）
- 1 単位 = 1 m、原点 = 戸塚駅付近 (35.4010, 139.5340)
- X = 東、Y = 上、Z = 南（北は -Z）。glTF/Three.js 準拠。Unity へは glTFast で読み込めば自動変換。

### 建物データの方針（国土地理院ベース）
- 建物の形・有無: 国土地理院ベクトルタイル（optimal_bvmap-v1 の BldA）。`tools/fetch_gsi.py`、デコーダは `tools/mvt.py`
- 高さ: 重なる PLATEAU 建物の実測高さ。無ければ種別（普通/堅ろう/無壁舎）と面積から推定
- PLATEAU にしか無い建物は使わない（取り壊し済みとみなす）
- `data/raw/gsi_bldg.json` を削除すると、下の PLATEAU ベースに戻る
- 自動分類（`build_city.py` の `classify`）: 国土地理院の種別（普通/堅ろう/無壁舎）・PLATEAU 実測高さ・面積・OSM の土地利用と店舗位置から
  `style`（house / apartment / commercial / industrial / lowrise / public / carport / parking / small）、`floors`（階数）、
  `roof`（戸建ての切妻/寄棟。実測高さ = 棟の高さとして壁を低くする）、`shops`（1階の店）を全建物に付ける

### 建物の形（点群から自動で作り直す）
神奈川県が公開している航空レーザ測量の点群（1㎡ あたり約 10 点、令和3年度測量、CC BY 4.0）から、建物 1 棟ごとの形を実測に合わせる。個別の指示は不要。
```
python tools/fetch_lidar.py     # 点群 8 図郭 (約 800MB) を取得 → data/raw/lidar_dsm.bin (0.5m の高さ格子)
python tools/fetch_ortho.py     # 航空写真 8 図郭 (約 90MB) を取得 → data/raw/ortho_rgb.bin (0.5m の色の格子)。Pillow が必要 (pip install pillow)
python tools/build_city.py      # 高さ格子があれば自動で適用
python tools/lidar_shape.py     # (build_city.py を通さず) 今の city.json にその場で適用。--undo で元に戻す
python tools/lidar_shape.py --repair   # 段が抜けた建物だけを直す (下の「段が抜ける不具合」)。何度実行しても同じ
```
`tools/lidar_shape.py` が輪郭の中の屋根の高さを読み、次を行う:
- **段**: 高さがなだらかにつながる所を「部分」に分ける（2階建ての母屋と平屋の下屋、ビルの低層部と高層部、塔屋）。低い段から順に「その高さ以上の所」の輪郭を積み上げる。上の段は別の建物データ（`part` = 元の建物の id、`minH` = 下の段の高さ、小さいものは `plain` = 窓なしの壁）
- **欠け**: 輪郭の中で地面の高さしかない所（中庭、輪郭が実際より大きい所）を建物から除く
- **屋根**: 部分ごとに 平ら / 切妻 / 寄棟 / 片流れ を当てはめ、棟の向き・勾配・軒の高さ・棟のずれ（`off`）を実測から決める。L 字やコの字は長方形に分けてそれぞれに屋根を付ける（`roofs`）
  - 当てはめの順: ① 長方形の屋根 → ② 長方形に分けて屋根（7 割以上を覆えたとき）→ ③ 輪郭に沿った寄棟（`t: "skel"`、高さ = 勾配 `k` × 輪郭までの距離。曲がった形や L 字にも掛かる）→ ④ 形は合いきらないが勾配はある場合の近似（平らより誤差が減るときだけ）→ どれも合わなければ平ら
  - 地面の高さのマスは屋根とつなげない。輪郭の端のマスは屋根より低いことが多いので、合わないマスが 3 割までなら採用する（`MIN_INLIER`）
  - 調査用: `lidar_shape.STATS = []` を入れてから実行すると、部分ごとの（面積, 高さのばらつき, 屋根の種類, …）がたまる
- **高さ**: PLATEAU の値を点群の値で置き換える（元の値は `lidar.h0`）
- **段が抜ける不具合（2026-11 に修正）**: 段の輪郭をまとめる `dissolve()` が、同じ角のはずの点を交点の計算誤差（0.0001 m）で別の点と数え、輪が閉じずに上の段を丸ごと捨てることがあった（ネクサスのコンフォートテラスは 20.9 m の建物が 9.1 m の平屋になっていた）。1 mm 以内の点を同じ点とみなすようにした。直す前に作った `city.json` には、段の抜けた建物が残っているので、`python tools/lidar_shape.py --repair` が、各建物を元に戻して直し直し、本体の高さ・段の数と高さが違うものだけ差し替える（違わない建物には触らない。外観を設定した建物は対象外）。点群との誤差は、中央値 0.23 → 0.16 m、建物ごとの上位 10% は 2.36 → 1.45 m、屋根が点群より 3 m 以上低い大きな建物は 33 → 1 棟
- 点群に写っていない建物（測量後の新築）、外観設定（`appearance.json`）の建物、修正モードで高さを変えた建物（`fixed`）、車庫は元のまま
- **屋根の色**: 航空写真（同じ配布元のオルソ画像, 25cm）の、輪郭の中の画素から屋根の色を読んで `rc` に入れる（段ごと。上の段が載っている所は除く）。輪郭の線から 0.75m 以内と、影（暗い側 35%）・てかりや設備（明るい側 15%）を除いた中央値。家の屋根が緑のときは木がかぶさっているとみなして付けない。写真そのものはゲームに貼らない。ゲーム側（`city.js` の `roofColor`）で、白っぽく写る分を少し締めて使う
- **壁の色**: Mapillary の路上写真（`tools/mapillary_walls.py`）。写真の位置・向き・画角から、壁の上の点（2 m より上、1.5 m × 1.2 m 間隔）が写真のどこに写るかを計算し、その色を読む。手前の建物・点群の木・地形（土手・擁壁）で隠れる点、35 m より遠い点、斜めすぎる面は使わない。建物ごとによく見える写真を 8 枚まで選び（2020 年以降を優先、同じ撮影から 2 枚まで）、暗い所（窓・影）・植木の緑・空を除いた明るめの所の平均を、写真どうしの中央値にする。2 枚以上・30 点以上でまとまった建物だけに付ける（鮮やかな色は、前に停まった車・バスを読まないよう、別々の撮影 2 回以上）。色味は明るさが中くらいの所、明るさの順位は明るめの所から取る。点群の表面で、手前の塀・防音壁・看板などに隠れる点と、その高さに建物が無い点（取り壊し・空き地）も除く。写真の下の方（車のボンネットなど）と、点から上端まで明るく平らな所（曇り空）も使わない。写真は露出や日陰で暗く写るので、明るさは全建物の中の順位を外壁らしい範囲（HSL の明度 0.50〜0.93）に当てはめ直し、淡い青・緑・紫のかぶりは無彩色に寄せ、色のはっきりした壁（レンガなど）は明るくしすぎない（`calibrate`）。上の段も同じ色。ランドマーク・敷地の外観を設定した建物は対象外。`python tools/mapillary_walls.py`（`--undo` で戻す、`--debug <建物 id>` で写真に点を打った確認用の画像）。写真は `data/raw/mapillary/` に置くだけで、ゲームには貼らない
- **ベランダの有無（路上写真を見て判定）**: 写真の位置ずれ（1〜3 m）があり、窓・ベランダの並びは自動では確かに読めない（試作で、はっきり読めた壁は 4 割ほど）。そこで `tools/facades.py sheet [x0,z0,x1,z1] [--max N]` が、集合住宅などの壁ごとにいちばんよく写った写真を選び、壁の輪郭を枠で描いた番号付きの一覧画像（`data/raw/mapillary/sheets/`）を作る。一覧を見て `python tools/facades.py label "0:b 1:w ..."` で壁ごとに b（ベランダあり）/ w（窓だけ）を付けると `data/facades.json` に入る（壁の中点と外向きで記録するので、輪郭を作り直しても近い壁に当てはまる）。`build_props.py` は判定のある壁はそれに従い（b は建物の種類・壁の向きによらず置く、w は置かない）、無い壁は今までの決まり（集合住宅の南寄りの長い壁）のまま
- 標準ライブラリだけで動く（numpy があれば取得が速い）。航空写真の取得（`fetch_ortho.py`）だけは JPEG を読むため Pillow が必要

### 空き地を埋める（点群と航空写真から自動で）
建物も道路も無い所は、元データに何も無いので以前は一色の地面だった。`tools/lidar_cover.py` が、建物の形と同じ点群・航空写真から次を読んで埋める。個別の指示は不要。
```
python tools/lidar_cover.py          # numpy が必要。先に fetch_lidar.py と fetch_ortho.py。最後に build_props.py も実行する
python tools/lidar_cover.py --undo   # 足した建物を消し、cover.json と data/lots.json を削除して元の見た目に戻す
```
1 m のマスごとに、点群の高さ・「葉を通り抜けた反射」の割合・反射の強さと、写真の色 (数値) を見る。写真そのものは貼らない。
- **地面の種類** (`public/data/cover.json`): 草 / 舗装 / 明るい舗装・砂利 / 土 / 木の下。地形の頂点 (2 m 間隔) ごとに 1 文字で、ゲームは地形の色に使う (`terrain.js` の `COVER_COLOR`)。追加の三角形は無い。
  草は反射が強く色味がある所、舗装は色味の無い灰色、土は茶色。影の中は反射の強さだけで決め、車や塀で読めないマスは周りの多数決で埋める。
  団地・商業地・工場・病院・寺社の敷地の一色の面は、これがあるときは描かない。見比べるときは URL に `?nocover`
- **木** (`data/lots.json` の `trees`): 地面より 2.5 m 以上高く、葉を通り抜けた反射が多い所。周りより高い点を高い順に拾い、実際の高さに合わせた大きさで置く。
  これがあるときは、公園・森・草地に乱数で散らす木は使わない。上限は約 14,000 本 (超えると間隔を広げる)
- **駐車場** (`parking`): 幅 9 m 以上・400 m2 以上の舗装のかたまり。車が 4 台以上写っているか、OSM の駐車場なら、駐車ますの白線を引く。
  車は点群に写っていたますにだけ置く。ますの向きは、かたまりを囲む一番小さい長方形の長い辺に合わせた推定
- **建物データに無い建物** (`city.json` に `src: "lidar"` で足す): 地面より 4.5 m 以上高く、木ではない、幅 5 m 以上・150 m2 以上のかたまり
  (高さの下限は `NEW_BLD_H` = 4.5 m。工事の仮囲いやトラックでかたまりがつながらない高さ)
  縁が切り立っていること (盛り土や斜面ではない) を確かめ、線路・ホーム・広場の上と送電鉄塔は除く。輪郭は 1 m の格子からの近似で、段・屋根・屋根の色は
  `lidar_shape.py` の同じ処理で付ける。種類は推定 (工業用地の中は industrial、ほかは高さで commercial / lowrise)
- **造成地** (`sites`): 土の地面が周り 25 m 四方の 2 割以上を占める、3,000 m2 以上のかたまり。それを囲む凸多角形の外周に工事の仮囲い (白い板) を置く。中の舗装には駐車ますを引かない
- 点群・写真は令和3年度。それ以降に変わった所は当時のまま (工事中だった所は工事中のまま)

### 塀・生け垣・物置・室外機（点群から自動で）
`python tools/lidar_small.py`（`--undo` で元に戻す）。点群を 0.5 m の格子にまとめ（地面の高さは `lidar_cover.py` と同じ推定）、`data/small.json` に書き、最後に `build_props.py` を呼ぶ。`props.json` の `yardWalls`・`sheds`・`acUnits` → `detail/yard.js`。
- 塀・生け垣: 地面から 0.8〜2.6 m のマスが細長く続く所（幅 1.2 m 以下・長さ 2.5 m 以上。塀の上面には 1 m に 1〜2 点しか当たらないので、1 m までのすき間をつなぎ、一直線に並ぶ区間をつなぐ）。その線のマスで、葉を通り抜けた反射が多いか航空写真で緑なら生け垣、それ以外はブロック塀。建物・道路・水面・駐車場・墓地・ホーム・森・畑・グラウンドの上と、木の枝先は除く
- 物置: 上が平らで高さ 1.8〜2.7 m、長さ 3 m 以下・広さ 1〜6 ㎡ のかたまりで、建物から 4 m 以内（軽自動車と見分けるため絞っている。駐車場の車の近くは除く）
- 室外機: 点群では小さすぎて読めない。戸建ての、道路から 5 m 以上離れた壁ぎわで、点群で何も無い所に 1〜2 台（決まりによる推定）
- 当たり判定あり（塀・生け垣は線、物置・室外機は箱）。低い塀はパルクールで飛び越えられる

### 線路まわり（電車・線路・柵・駅の中）
配置は `build_props.py`（`props.json` の `rail` と `fences`）、形は `detail/` の各ファイル。
- 走る電車（`detail/trains.js`）: `rail.routes` = 線路の区間を端点でつないだ、地図の端から端までの道筋（`build_train_routes`。名前で東海道線・横須賀線・貨物線に分け、分かれ道では同じ線・いちばんまっすぐな区間を選ぶ。左側通行なので、反対向きの線路が右 3〜15 m にある向きだけを残す。約 5 m おきの点、y = レールの上面）。旅客線は 15 両で戸塚駅のホームに 30 秒止まり、貨物は機関車 + コンテナ車 19 両で通過。80 km/h・加減速 0.9 m/s²、5〜12 分おき。時刻は実際の時計なので、だれが見ても同じ所を走る。色は一般的な近郊電車の配色（特定の形式の再現ではない）。`?trainAt=秒` で時刻を固定、`?notrain` で走らせない。当たり判定は無い
- 線路（`detail/trackbed.js`）: 砕石の模様、コンクリートの枕木（0.6 m おき）、立体のレール（狭軌 1,067 mm、上面 = 地形 + 0.55 m。`build_props.py` の `RAIL_TOP` と同じ）。線路の橋の上は `bridges.js` のまま
- 柵（`build_rail_fences`、`fences` の `kind: "rail"`）: いちばん外側の線路の外側 3.2 m に高さ 1.8 m の金網。外側 25 m 以内にまだ線路がある所・道路・建物・ホームから 8 m 以内は空ける。踏切は範囲内に無い（道路と線路が平面で交わる所が無い）
- 駅の中（`build_station_fixtures`）: 駅舎（線路の上の建物）を支える柱（線路の中心から 2.4 m 以上離れた所に約 9 m おき）、ホームから駅舎へ上がる階段（各ホーム 1 か所。上れない。箱の当たり判定）、ベンチ・駅名標・自販機

### 敷地（工業用地・学校・墓地・寺社・病院）
OSM の土地利用のうち、工業用地 (`industrial`)・墓地 (`cemetery`)・寺社 (`worship`)・病院 (`hospital`) も `city.json` の `areas` に入れる (ミニマップに色が付く)。
`build_props.py` が、工業用地・学校・墓地の外周に柵を置く。輪郭が道路の上を通る所は内側へ最大 10 m ずらし、ずらしても道路や建物に当たる所 (門・出入口) は空ける。墓地には墓石を並べる (向きは一番長い辺に合わせた推定)。

### 建物データの方針（旧: PLATEAU ベース）
- 建物の形と高さは PLATEAU (LOD1, 実測高さ) を正とする。戸塚エリアは LOD2/テクスチャ未整備 (2020/2022/2024 年度版で確認)。
- 名前・種別 (house 等)・色は位置の重なる OSM 建物から引き継ぐ。
- PLATEAU に無い OSM 建物 (高架・庇など) は補完として残す。
- 各建物の `e` = 原点付近の地盤からの相対標高 (m)。地形対応時に使用。現状は平地として描画。

範囲を変えるときは `tools/config.py` の `BOUNDS`（原点からのメートル）を編集。

### 小物の配置 (props.json)
`tools/build_props.py` が `city.json`・`terrain.json` から作る。座標は `city.json` と同じ（x = 東、y = 上、z = 南、1 = 1m）。
- `y` はその場所の地面の高さ（`terrain.json` と同じ補間）。`yaw` は Y 軸まわりの回転（ラジアン）で、物の正面（局所 +Z）が (sin yaw, cos yaw) を向く（three.js の `rotation.y` と同じ）
- `poles` 電柱（`transformer` 変圧器あり、`lamp` 街灯あり。正面が道路側）／`wires` 電線 `[ax, ay, az, bx, by, bz, たるみ]`（中央で たるみ m 下がる放物線）
- `paint` 横断歩道の縞・停止線、`tomare`「止まれ」の文字: 長方形 `[中心x, 中心z, 長さの向きdx, dz, 長さ, 幅]`。路面に沿わせて描く
- `guardRails` ガードパイプ: ひと続きの柵ごとの支柱の列 `[[x, z, y], ...]`。隣どうしを高さ 0.45m と 0.8m のパイプでつなぐ
- `vending` 自販機（`color` 0=赤 1=青 2=白、正面が道路側）／`mirrors` カーブミラー
- `signals` 車両用信号（`reach` 腕の長さ、`axis` 0=主方向 1=交差方向、`offset` 周期のずれ 秒。周期は 青22→黄3→全赤2 秒 × 2 方向）／`pedSignals` 歩行者用信号（正面が向かい側）／`busStops` バス停（`name`）
- `balconies` 集合住宅のベランダ（壁ごと）: 壁の始点 `x, z`、壁の向き `dx, dz`、外向き `nx, nz`、壁の長さ `len`、建物の基準の高さ `y`、1 階分の高さ `floorH`、階数 `floors`、`dark`（濃い色の手すり）、建物の id `b`。2 階から最上階まで、床の高さ `y + k × floorH`（k = 1 〜 floors−1）に、奥行き 1.1m・手すり壁 1.1m のベランダを付ける（壁の両端 0.4m は空ける）
- `signs` 店の看板と日よけ: 看板の中心の位置 `x, z`（店の点にいちばん近い壁の線の上で、店の点を壁に投影した位置。看板が壁からはみ出さない範囲に寄せる。壁の外向きと逆側にある壁は不利にする）。`face` = 店先の柄（`glass` ガラスの店先 / `lattice` 居酒屋の格子戸。看板の下の壁に貼る。ランドマークの建物と幅 2.4 m 未満の壁には付けない。夜は中の明かりが光る）、建物の基準の高さ `y`、正面 = 壁の外向き、幅 `w`、`name`、`cat`、`colors`（地・文字・帯と日よけの色）、建物の id `b`。看板は `y + 3.35`、日よけは `y + 2.6`。チェーン店（`tools/build_props.py` の `CHAINS`。セブン・ローソン・ファミリーマート・マクドナルド・スターバックス・吉野家・松屋・すき家・ガスト・サイゼリヤ・ドトール・ミスド・ダイソー・銀行 3 行）は、店名から決まった配色が付き（`chain`）、帯と日よけは `bands` の色を並べる（セブンはオレンジ・緑・赤の 3 色）。ロゴは使わず色と帯と店名の文字だけ。路上写真で確かめた配色（セブン・マクドナルド）以外は、一般的な配色の推定。`CHAINS` に 1 行足せば増やせる。チェーン以外の個人店は、`tools/shopfronts.py`（`sheet` で店ごとに近い写真を切り出した番号付きの一覧画像を作り、見て `label` で日よけの色 `a=`・のれん `n=`・提灯 `l`・看板の色 `s=地/文字` を付けると `data/shopfronts.json` に入る）の判定を `build_props.py` が読み、看板に反映する（`front: "photo"`）。居酒屋（`amenity=pub / bar`）で判定が無い店は、標準ののれん（濃紺）と赤ちょうちんを付ける（`front: "default"`、推定。提灯は夜に光る）
- `trees` 木: `[x, z, y, 大きさの倍率, 0〜1 の乱数]`。乱数は向き（× 6.28 ラジアン）と葉の色の濃さに使う。基準の木は幹の高さ 2.2m、葉は高さ 3.2m を中心に半径 1.7m。
  位置は `data/lots.json`（点群で見つけた木。大きさ = 実際の高さ ÷ 4.9 m、建物に近い木は葉が壁に入らない大きさに縮める）。無ければ公園・森・草地に乱数で散らす
- `cars` 駐車場の車: `x, y, z, yaw`、車体の色 `c`。駐車ますの白線は `paint` に入る
- `fences` 敷地の外周の柵（種類ごと）: `kind`（industrial / school / cemetery は金網、construction は工事の仮囲いの白い板）、`color`、高さ `h`、柱 `posts` `[x, z, y]`、パネル `panels` `[中心x, 中心z, y, yaw, 長さ]`
- `graves` 墓石: `x, y, z, yaw`
- `bigSigns` ランドマークの壁面の大きな看板: 壁の中点 `x, z`、看板の中心の高さ `y`、正面 = 壁の外向き、幅 `w`、高さ `h`、`text`、`bg`・`fg`（地と文字の色）、建物の id `b`
- `rail` 駅と線路（描画は `public/src/detail/station.js`）
  - `platforms` ホーム: 両縁の点列 `left`・`right`（約 4 m ごと）と、各点の上面の高さ `y`（地面 + 1.1 m。川をまたぐ所は前後の高さでならす）。黄色い点字ブロックと縁の白線は描画側で引く
  - `canopies` ホームの屋根: 同じ形で `y` = 屋根の下面の高さ。ホームの両端 8 m と幅 3 m 未満の所には付けない／`columns` 屋根の柱 `[x, z, 下端 y, 上端 y]`
  - `gantries` 架線柱（門形）`[中心 x, 中心 z, 地面 y, 線路に直角な向き dx, dz, 半幅]`: 線路を 50 m ごとに歩き、直角に横切る線路をまとめて 1 つの門にする。ホーム・建物に掛かる所には作らない／`catenary` 架線の線分（線路の真上 5 m）
- `walk` 歩道橋・デッキ・階段の手すり（描画は `public/src/detail/walkways.js`）: `rails` = `{k, p}` の列。`p` は路面の縁の線 `[[x, y, z], ...]`（y = 路面の高さ）、`k` は `deck`（高欄）/ `stair`（デッキへ上がる階段）/ `ground`（地面の階段）。`dims` に高さ
- `sites` 敷地の外構（`data/appearance.json` の `sites` から）: 庭（芝生のマス・通路・噴水・円すいの木）、門のアーチ、円形広場、エントランス棟の正面、屋上の塔、日よけ、花壇、オベリスク、天窓、フェンス
- `colliders` 当たり判定。y0, y1 は下端・上端の絶対高さ
  - `circle` `[x, z, 半径, y0, y1]`（電柱・信号の柱・ミラー・噴水・木など）
  - `box` `[x, z, yaw, 局所Xの半幅, 局所Zの半幅, y0, y1]`（自販機・フェンス・花壇など）
  - `line` `[半幅, 高さ, x0, z0, y0, x1, z1, y1, ...]`（ガードパイプ、デッキ・階段の手すり。折れ線に沿った薄い壁）
  - `tree` `circle` と同じ形（木の幹）。木は V キーで消えないので、この判定も常に有効
  - ブラウザでは移動・着地・ワープ先の判定だけが使う（カメラは建物だけを見る）。V キーで小物を消すと当たり判定も外れる。看板・日よけ・ベランダなど頭より上の物と、電線には判定がない

### 道路（PLATEAU の道路面）
`tools/fetch_plateau.py` が PLATEAU の道路 LOD1 面（測量に基づく道路の範囲。歩道・車道の区別なし）も取得し `data/raw/plateau_road.json` に保存。`build_city.py` の `process_roads` が:
- `roadAreas`: 道路面をそのまま描く（実際の道幅・交差点の形）
- OSM の各道路に `cov`（区間ごとに PLATEAU 面で覆われているか）、`w`（実測の幅。元の値は `w_osm`）、`half`（中心線から左右の縁まで）、`sw`（幹線の歩道幅の推定）を付ける
- 覆われた区間は OSM の帯を描かない。私道・遊歩道など PLATEAU に無い区間だけ OSM の中心線から描く
- 路面の白線（`public/src/city.js`）: 中央線は、隣に平行な車道が無い幅 16 m 以下の幹線だけ。幅 16 m 超の道や並走する車道がある道は、幅 ÷ 3.25 m を車線数として等分した破線の車線区切り（路面が重なる並走道路は片方だけに引く。交差点の中は引かない）。車線数は推定で、実際の車線数とは限らない。外側線（`addEdgeLines`）は道路面の縁から 0.35 m 内側に自動で引く。隣の面との境界・橋・歩道を推定した幹線・私道は除き、住宅街の道は幅 5.5 m 以上だけ
- 電柱・ガードパイプ・横断歩道・停止線・自販機は実測の縁と車道の中心に合わせる。歩道の帯は交差点の手前で切る

### 橋・歩道橋・デッキ
標高データは地面だけなので、橋はそのままだと川底や下の道路まで沈む。`build_city.py` の `compute_bridges` が橋（bridge=yes）の各頂点の高さ `ys` を計算する:
- つながった橋をまとめ、地面の道とつながる点（たもと）を地面の高さに固定して間をなめらかに補間
- 道路・線路の上を渡る所は下をくぐれる高さ（道路 5.3m・線路 6.8m）を確保し、勾配（車道 8%・歩道 12%・階段 70%）で下げる
- 持ち上がった歩道橋につながる地面側の歩道・階段は坂（`ramp`）にする
- ゲーム側 `public/src/bridges.js` が路面・側面・底面・橋脚（車道の橋は高欄も）を作り、`deckAt()` で上を歩ける。車道の橋の部分の PLATEAU 道路面は描かない

#### デッキ・階段の高さを実測に合わせる（`tools/deck_heights.py`）
上の推定だと、実際は水平なデッキや高架が全体に坂になり、階段の勾配もまちまちで継ぎ目がずれる。点群があれば、橋（車道の橋も）とそこへ上がる階段・坂（`ramp`）の高さを実測に置き換える。個別の指示は不要。
```
python tools/deck_heights.py            # 今の city.json にその場で適用 (先に fetch_lidar.py)。最後に build_props.py も実行する
python tools/deck_heights.py --report   # 道ごとに「測った高さ」と「決めた高さ」を並べて表示 (調べるとき用)
```
- 中心線を 0.5 m ごとに測る（左右 ±1 m の中央値）。隣と 1 m 以上飛ぶ所で面を分け、下の面より 1.8 m 以上高い面・近くの大きなデッキより 2.6 m 以上高い面は屋根とみなして捨てる
- 橋の上で地面が写った所（細い橋と中心線のずれ）は「不明」。地面の道とつながる頂点は地面に固定。不明な所は両側からなめらかに補う
- 階段は、下から上へ単調に上がる測点だけを使う。実測が半分に満たない階段は両端を直線で結ぶ。先が建物に入る階段の端は固定しない
- 高さが折れる所に頂点を足す（元の頂点の番号は `base` に控える。何度実行しても同じ結果）。`build_city.py` も `compute_bridges` の後に同じ処理を呼ぶ
- 車道の橋は、たもとの地形と実測が 1.2 m 以上合わないもの（川岸の地形が低すぎる橋など）は元の推定のまま。区間ごとの `cov` は足した頂点にも引き継ぐ
- 読めなかった所は `data/appearance.json` の `deck_levels` で補える: `{"x", "z", "r", "y"}` =（x, z）から r m 以内のデッキの高さを y にする
- 戸塚駅では、東口のデッキが高さ 6.8 m と 4.5 m の 2 段、西口が 8.1 m 前後で水平、と読めた（実測できた測点は 57%。残りは屋根の下・建物の中で、補間）

#### 高架の下の地形（`tools/terrain_bridges.py`）
地形は点群の各マスの最低点から作ってあるので、幅の広い高架の下は「高架の路面」が地面として入り、高架に沿って土手のように盛り上がる（下をくぐる道路や横断歩道が斜面に貼り付いてうねる）。
```
python tools/terrain_bridges.py          # terrain.json を書き換える (numpy が必要。先に fetch_lidar.py)。最後に deck_heights.py と build_props.py も実行する
python tools/terrain_bridges.py --undo   # 元に戻す
```
- 橋の路面の範囲 + 4 m を「橋の下」とし、各頂点から橋に直角な両方向へ範囲の外まで進んで、そこの地面の高さを見る
- 両側とも低い所だけ、高い方の地面の高さまで下げる。片側が高い所（橋が高台や、地形として入っている広場の縁に載っている所。例: 西口のバスセンターの上の広場）は削らない
- 点群の表面（= 橋の路面）が、下げた後の地面より 1.5 m 以上高い所だけ（地面と同じ高さの橋・川の上の橋は変わらない）
- 輪郭の頂点の地面が下がった建物は、屋根の高さを保ったまま基礎を下げる
- 元の高さは `terrain.json` の `patch` に控える（何度実行しても同じ結果）。橋の高さ `ys` には依らない
- 最後に `deck_heights.py` も実行する（橋・階段のたもとは地面に固定するので、地面を直した後に高さを決める。逆の順だと階段の下端が浮く）
- `build_city.py` からは呼ばない。`build_city.py` を通しで実行した後は `terrain_bridges.py` を実行する
- 続けて `tools/plaza_edges.py` が駅前の人工地盤（広場）の縁を作る（下の「広場の縁」）
- 車道の橋の路面は、PLATEAU の道路面から測った左右の幅（`half`）で描く（`public/src/bridges.js`）

#### 広場の縁（`tools/plaza_edges.py`。`terrain_bridges.py` から呼ばれる）
駅前の人工地盤（例: 西口のバスセンターの上、高さ約 3 m）は橋のデータに無く、地形の盛り上がりとして入っている。地形は 2 m 間隔でぼやけるので、縁が斜面になり、明かり取りの穴がすり鉢状にへこむ。
- 点群の表面（1 m 格子）から「高い面」（周り 10 m の一番低い地面より 2 m 以上高く、近くの地形の高さと同じ。建物の中・縁 1 m は除く）を取る
- 歩行者用の橋から 6 m 以内に届き、150 m² 以上で、平ら（高さの 10〜90% の幅が 1.2 m 以下）なかたまりだけを広場とみなす。川沿い（護岸）は除く
- かたまりの輪郭（穴も）のうち、外側 5 マスのうち 3 マス以上が 1.8 m 以上低い所を「縁」とし、直線にならす。屋根・デッキの下で地面が写っていない所は、地形が低ければ低いとみなす
- 縁の内側に幅 2.5 m の床（`roads` に `edge: 1` の歩行者用の橋として足す）を置く。外側の側面は地面まで下ろして壁にする（`bridges.js`）。手すりは `build_walk()` が付ける。既にある橋の路面と重なる部分には床を置かない
- 縁の外側 6 m の地形を下の地面まで落とし、床の下で広場の高さへ上げる。元の地形は `terrain.json` の `patch_edges` に控える（`terrain_bridges.py --undo` で一緒に戻る）
- 橋の高さ `ys` は使わない（何度実行しても、`--undo` の後でも同じ結果になる）。戸塚駅まわりで 15 本・177 m

#### 手すり・高欄（`build_props.py` の `build_walk()` → `props.json` の `walk` → `public/src/detail/walkways.js`）
- デッキ・歩道橋の両縁に高欄（高さ 1.1 m。支柱 1.5 m ごと・笠木・下の横桟・縦格子）、デッキへ上がる階段と急な坂に手すり（0.9 m、2 段 + 縦格子）、地面の階段に手すり（0.9 m、2 段、ステンレス色）。幅 4 m 以上の階段は中央にも 1 本
- 置かない所: ほかの通路がつながる所（同じ高さの路面の中。車道の橋の上の歩道も含む）、建物に入る所、地面すれすれの所。どこにもつながらず宙で終わる端はふさぐ
- 歩道でも勾配が 0.22 より急な区間は段にする（`public/src/stairs.js`。実測で段差になっている所）。坂（`ramp`）も地面から浮いている区間は側面・底面・柱を作る
- 形は「よくある形」で、1 本ごとに実物と合わせてはいない。色・形を決める元データが無いため

### 地形（坂）
`tools/fetch_dem.py` が国土地理院の標高タイル（DEM5A＝航空レーザー5mメッシュ、欠けは DEM5B/10B で補完）から 4m 間隔の標高グリッド `public/data/terrain.json` を作る（戸塚駅付近＝0m の相対標高）。
- ゲーム側 `public/src/terrain.js` の `H(x, z)` が地面の高さ。地形メッシュと同じ三角形補間なので、置いた物が浮いたり埋まったりしない
- 道路・川・公園などの平面は `drape()` で細かく割って地形に沿わせる
- 建物は `build_city.py` が基礎の高さ `y`（輪郭で一番低い地面）を付け、高さ `h` は基礎からの値のまま
- `terrain.json` を消すと平らな地面に戻る
- 現在の `terrain.json` は **2m 間隔**。点群（`data/raw/lidar/`）の各マスの最低点で作り（`tools/lidar_terrain.py` → `export_terrain_hi.py`）、点の無い所は DEM との差を補って埋めている。この点群は分類（地面など）が当てにならないので、分類は使わない。DEM 版（4m）に戻すなら `python tools/fetch_dem.py` を実行する（その後 `retarget_terrain.py` で建物の高さを合わせ直す）
- 地形を差し替えたあとは `tools/retarget_terrain.py <古い> <新しい>` で `city.json` の建物の基礎・地面にある橋の頂点を動かし、`build_props.py` を実行する（`build_city.py` を通しで実行できない環境用）
- 傾斜で地形を色分けする（法面は緑、擁壁・崖は灰色）。擁壁の壁は `fetch_osm_walls.py` → `lidar_walls.py --osm` → `walls.json`（URL に `?walls` で表示。見た目が不十分で試作）
- 階段（OSM の steps）は `stairs.js` が段を作り、`stairAt()` で階段の上かを判定してキャラの動きを変える
- 描画: 対数深度バッファは使わない（内蔵 GPU で約 2 倍遅い）。切り分け用に URL で `?perf`（タブにフレームレート）・`?log`・`?near=`・`?pr=`・`?noaa`・`?noshadow`
- カメラの自動追従（`camera.js`）: 横や斜めへ進むとキャラの背中側へゆっくり回り込み、見下ろし角は約 17° に戻る。マウスで視点を動かした直後は手動を優先し、0.8 秒後から効き始める。カメラへ向かって来るとき（S）・止まっているとき・修正モード中は働かない。速さと角度は `camera.js` 先頭の `FOLLOW_*`、URL に `?nofollow` で無効

### パルクール（public/src/parkour.js・player.js・world.js・character.js）
走り・ダッシュで障害物へ向かっているとき（歩きでは発動しない）、足元から上端までの高さと奥行きで動きが決まる。

| 動き | 条件 | 内容 |
|---|---|---|
| 飛び越え（vault） | 高さ 0.4〜1.25 m、奥行き 1 m 以下、向こう側に降りられる | 片手をついて脚を横へ流して越え、速さを保って走り続ける |
| 飛び乗り（hop） | 高さ 0.4〜0.9 m、上に立てる | 手を使わずに飛び乗る |
| よじ登り（climb） | 高さ 2.3 m まで（手を上げて届く高さ）、上に立てる | 縁に両手をかけ、体を引き上げて上に立つ。上に立てない薄い塀は、越えて向こう側へ降りる |

- 空中でも同じ判定をするので、ジャンプ・2 段ジャンプで縁が手の届く高さ（足元から 2.3 m）に入ると、つかんで登る。
- 判定は `world.js` の `probeLedge()`（進む向きの先の壁・上端の高さ・奥行き・立てるか・降りられるか）。上に別の建物が重なっていて頭が入らない所、壁に沿って斜めに走っているだけのときは発動しない。
- 勾配屋根の建物は、壁から 0.45 m 張り出した軒先が縁になる（高さは軒先の屋根の高さ）。軒の下に入り込んでいるときは、いったん下がって軒先をつかむ。登った先は屋根の斜面の上。
  そのために当たり判定（`world.js` の `top()`）は、勾配屋根を「棟の高さの平らな箱」ではなく、描画と同じ斜面の高さ（`city.js` の `addPitched`・`addSkelRoof` と同じ式）で持つ。屋根の上は斜面に沿って歩ける。
- 動いている間は操作を受け付けず、`parkour.js` の道筋（進んだ距離と足元の高さ）の上を動く。高さの決まり（`REACH_H` など）と所要時間もここ。
- 姿勢は `character.js` の `actPose()`。腕は肩から縁へ届く角度を計算し、残ったずれは手が縁の高さに来るよう腰の高さを動かして合わせる（VRM でも同じ）。
- 確認: `node tools/dev/charshot.js <出力フォルダ> "act=vault&h=0.85&s=0.5" "act=climb&h=1.9&s=0.4"`（キャラと箱だけを撮る。1 枚数秒）。

- **高い所からの着地の前転**（動きのデータ `ual_roll` = Quaternius の `Roll_RM`）: 約 2.75 m 以上（落ちる速さ 11.5 m/s 超え）から、横に 2.5 m/s より速く動きながら着地すると、しゃがむ → 前へ飛び込む → 肩から転がる → 起き上がる（データの 0〜1.2 秒を 1.5 倍速 = 0.8 秒、約 4.7 m 進む）。2 段ジャンプで平らな所に降りただけ・止まって着地したときは前転しない。前へ進む距離はデータの腰の動きから、転がっている間の腰の高さもデータのまま（`player.js` の `ROLL`・`startRoll()`・`updateRoll()`、`character.js` の `actPose()`）。
- 台への飛び乗りは、空中の姿勢（動きのデータのジャンプ）と着地の動きをそのまま使う。
### 攻撃（public/src/attack.js・player.js・character.js）
**今は 3 撃目（回転斬り）までの 3 連撃**（持ち主の希望。`attack.js` の `COMBO_MAX` = 3。3 撃目の次は 1 撃目から。4・5 撃目の動きと処理は残してあり、`COMBO_MAX` を 5 にすれば戻る）。
普段は剣を持っていない。攻撃ボタン（J・左クリック・スマホは「攻撃」）を押すと両手に剣が現れ、最後の攻撃から 5 秒（`SWORD_IDLE`）たつと消える。地上で押すと始まり、続けて押すと次の手順に進む（手順が終わってから 0.3 秒以内の入力も続きとして受ける）。

| 手順 | 動き |
|---|---|
| 1 | 右の剣を右肩の後ろ高くへ振りかぶってため、右足を体の前を横切って左へ踏み込みながら（左斜め前へ約 2 m 動く）、腰 → 胸 → 腕の順に回して左へ大きく振り抜く。振り抜いたときは真横を向き、沈んだまま一瞬止めて（残心）正面へ戻る |
| 2 | 左の剣で、1 と左右逆（左足が右へ交差して、右斜め前へ動く） |
| 3 | 回転斬り: 右へねじって両腕を引きつけてため、両腕を水平に広げて左回りに 1 回転しながら前へ約 3 m すべる（体ごと回す）。低く構えて止まり、足元に輪の形の土ぼこり |
| 4 | 片膝立ちまで沈んで剣を下げてため、跳び上がりながら二刀を真上へ斬り上げる（高さ約 2.5 m、跳ぶ瞬間に土ぼこりの輪）。空中で横に 2 回転し、頂点で一瞬浮く |
| 5 | 4 の空中（頂点のあたりから）か、着地した直後に押す。頂点で二刀を頭の後ろへ振りかぶり、前斜め下へ急降下しながら十字に斬る（十字の閃光）。片膝で着地して（衝撃の輪・土ぼこり）2〜3 m 滑り、二刀を左右へ広げて立ち上がり、剣を手の中で 1 回まわして構える |

- 動いている間は操作を受け付けず、手順ごとに踏み込む（1・2 は前へ 1.2 m・横へ 1.5 m、3 は前へ 2 m。`STEPS` の `move`）。振り抜く・着地する瞬間に 0.06 秒ほど動きが止まる（ヒットストップ、`stops`。1・2・3・5 の十字と着地）。軌跡は手順ごとに太さ・長さ・濃さを変える（`TRAIL_STYLE`）。土ぼこり・十字の閃光・衝撃の輪は `FX`（時間と種類の表）で、`character.js` の `runFx`・`updateFx` が出す。体ごとの回転（3・4）は `spinAt()`、剣を手の中でまわす動き（5 の締め）は `TWIRL`。始めるときに移動キーを押していれば、その向きへ向き直る。押す入力は手順の途中でも覚えておき、動きが振り切れたところで次へ移る。
- タイミング・踏み込み・姿勢の表は `attack.js`。姿勢は「腰と胸のひねり・前傾・両手の位置（肩から見た位置）・足の出し方・しゃがみ・脚の向き（1 で脚ごと腰の向きへ回る。横へ交差して踏み込む形）」で、キーの間をなめらかにつなぐ。
- 腕は `character.js` の `armIK()` が手の位置から解く（肘は前へ曲がる 1 軸）。肩はクォータニオンのまま骨に渡す（オイラー角だと腕を高く上げたときに不連続になるため）。VRM でも同じ。
- 剣は握った手から前腕の向きに伸びる。軌跡は刃の先と根もとの世界座標を残すリボン（`TRAIL` の時間だけ。0.18 秒で消える）。
- 確認: `node tools/dev/charshot.js <出力フォルダ> "atk=1&ph=0&t=0.2" "atk=4&ph=1&t=0.14&air=1"`（手順・局面・時間。空中は `&air=1`）。


#### 動きのデータ（URL に `?handmade` で以前の手作りに戻す）
手作りの姿勢の代わりに、動きのデータ（骨の向きをコマごとに並べたもの）で動かす仕組み。データは Quaternius「Universal Animation Library」の無料版（**CC0 1.0**、作者 Quaternius）。使っているもの:
- **待機・歩き・走り・ダッシュ**: `Idle_Loop`・`Walk_Loop`・`Jog_Fwd_Loop`・`Sprint_Loop`。速さで 3 つを混ぜ（歩き 1.6 m/s はほぼ歩き、走り 5.5・ダッシュ 10 は全力疾走を速めて再生）、左足が前へ出る時をそろえて、1 周で進む距離に合わせて位相を進める（足が滑らない）。進む速さはデータから測った値に、このキャラの脚に合わせた補正（`character.js` の `LOCO_K`）をかけた。**階段は手作りのまま**（データに階段の動きが無い）。
- **ジャンプ**: 上がっている間は `Jump_Start` の後半（脚を抱える）、落ちている間は `Jump_Loop`、着地の直後は `Jump_Land`（落ちた速さで深さを変え、走っているときは浅く）。

### マルチプレイ（public/src/net/・server/）
同じ街に入った人どうしが見え、「戦闘オン」にした人同士で攻撃が当たる。**標準では無効**で、`public/src/net/config.js` の `SERVER` にサーバーの URL を書いたとき（または URL に `?mp=wss://…` を付けたとき）だけ働く。サーバー（Cloudflare Workers の無料プランで動く構成）の中身・公開のしかた・お金の注意・決まりの数字は `server/README.md`。

- **つなぎ方**: 開いた直後は 1 人用（通信しない）。左上の「みんなと遊ぶ」（O キー）を押したときだけ、だれでも入れる部屋（16 人まで。満員なら次の部屋）に入る。「1 人に戻る」（O キー）で抜けると、通信を切って 1 人用に戻る。`?room=合言葉` で、同じ合言葉の人だけの部屋。名前はサーバーが自動で付ける（入力・チャット・アカウントは無い）。
- **送るもの**: 自分の位置・向き・速さ・動き（攻撃の手順と時間、パルクールの進み具合、のけぞり・倒れ）を 1 秒に 8 回（`player.js` の `netState()`）。立ち止まっている間は 2 秒に 1 回。サーバーは 0.1 秒ごとに、動いた人の分をまとめて配る。
- **ほかの人の表示**（`remote.js`）: 届いた状態を 0.22 秒遅らせ、前後 2 つの間をつないで見せる。姿は軽い組み立て式のキャラで、服の色を人ごとに変える（VRM は自分だけ。スマホのメモリの節約）。220 m より遠い人は描かない。頭上に名前、戦闘オンの人は赤い名前と体力。ミニマップに点（戦闘オンは赤）。
- **戦闘**: B キー / 画面の「戦闘」でオン・オフ。当たったか・体力はサーバーが決めて全員に知らせる。当てられると、飛ばされてのけぞり（0.35 秒操作できない。`player.js` の `hurt()`）、画面のふちが赤く光る。体力が無くなると膝をつき、3 秒後にスタート地点で復活する。
- **押し合い**（`player.js` の `separate()`）: ほかの人と重なると、重なった分を少しずつ押し離す（かたい壁にはしない。相手の位置は通信の遅れで少し過去なので、急に押し戻すとカクッとなるため）。戦闘オン・オフに関係なく、だれとでも。動かすのは自分だけで、相手は相手の画面で同じように離れる。上下に 1.6 m 以上離れた人（デッキの上と下など）、倒れている人、パルクール中は押さない。人はパルクールの障害物にしない（飛び越え・よじ登りは柵・塀・建物だけ）。計算は近くの最大 15 人との距離だけで、重さへの影響はほぼ無い。
- 確認は `node tools/dev/mpcheck.js <出力フォルダ>`（手元のサーバー + ヘッドレスブラウザ 2 つ）。

### キャラクター（public/src/character.js）
- 標準では、関節のある人型（腰・背骨・胸・首・頭・肩・肘・股関節・膝・足首）を組み立てて動かす。歩き・走りは、足が地面に着いている間は滑らず浮かないように角度から腰の高さを計算している。
- `public/models/player.vrm` を置くと、そのキャラに差し替わる（VRoid Studio で作った VRM 0.x / 1.0 に対応。読み込みは `@pixiv/three-vrm`、`index.html` の importmap）。同じ角度をモデルの人型ボーンに渡すので、歩き・走り・ジャンプ・髪や服の揺れ・まばたきが動く。ファイルが無い・読めないときは標準のキャラのまま（コンソールに理由が出る）。
- 大きさは自動で合わせる（足裏が地面、腰の高さが標準と同じ）。モデルは配布・利用規約を確認してから置く。
- 今入っているモデルは、VRoid Studio 公式のサンプル「AvatarSample_A」（VRM 0.x、約 15MB。CC0 ではなく利用条件付き）。出どころは `public/models/README.md`。別のモデルにするときは、同じ名前で上書きする。
- 動き: 走り（5.5 m/s）は肘を曲げて前腕を外へ開いて振り、前傾して弾む。歩き（1.6 m/s）は腕を伸ばしぎみに静かに振る。どちらも内股で、手首を外へ反らし、指を軽く握る（指は VRM のときだけ）。立っているときは体重をゆっくり移し、首を少しかしげる。
- 表情: VRM では少しだけ笑顔にしている（強さ 0.35）。URL に `?smile=0.2` のように付けると強さを試せる（0 で無表情）。
- 走りで髪が跳ね上がらないよう、VRM では腰の高さの変化をなまらせている（`HIP_SMOOTH`）。その分、着地で足が地面からわずかにずれる。

### 外観設定（data/appearance.json）
敷地（OSM の名前付き住宅地エリア）ごとに、建物の外観と外構を設定する。物件情報の公開写真を見て特徴を書き起こしたもの（写真自体は保存・使用しない）。
- `buildings.set`: `floors`（階数）, `color`（外壁色）, `facade: "euro"`（ベージュ外壁＋奥まったバルコニー）, `mansard`（最上部の濃い色の帯）, `balcony: "all"`（全ての長い面にベランダ）, `railing`
- `garden`: 最大の棟のコの字の内側に芝生・レンガの通路・噴水・円すい形の木
- `fence`: 敷地境界の金属フェンス（建物に接する部分は省く）
- `gate`: 指定位置の建物を通り抜けられる門（両側の柱＋上の梁＋アーチ）に置き換える。門の前はフェンス・ガードパイプを切る
- `hall`: エントランス棟（アーチ窓・赤い扉の正面）、`plaza`: 噴水のある円形広場、`turrets`: 屋上の塔（ドーム）、`awnings`: 中庭側1階の日よけ
- 庭には花壇・オベリスク（エントランス側）・丸い天窓（反対側）も置く。`garden.layout` があれば、その配置で作る（グランシティ: 航空写真で測った位置。`circles` 石張りの円形の広場と中央の噴水・オベリスク、`paths` レンガの通路 `[[x0, z0], [x1, z1], 幅]`、`panels` 白い縁の芝の区画（四隅に円すい形の木）、`hedges` 刈り込んだ生け垣、`planters` 丸い植え込み）
- `frontage`: `guard: false` で敷地の道路ぎわ（敷地の輪郭から 3 m 以内）にガードパイプを置かない、`fence: false` で車の通る道路の端から 3 m 以内に敷地の柵を置かない
- `carpark`: 立体駐車場の入口。道路側の壁 `a`→`b` の `t` m の所の 1 階に黒い鉄の門（上がアーチ、奥は暗い開口）、前にレンガ色の舗装と駐車ます（`lot`）。描画は `detail/clockhouse.js` の `buildCarpark`
- 門・エントランス棟・広場・塔の座標は、建物データの配置と写真の見え方からの推定（手置き）
- 現在はグランシティ パレ・ド・リヴァージュ（7階建・RC造・2005年築）のみ

#### 目印になる大きな建物（`landmarks`、`tools/landmarks.py`）
駅前の商業ビルなど、敷地ではなく建物 1 棟に外観を設定する。公開されている説明文（階数・各階の用途・テーマカラー）と、航空写真・点群の観察から書き起こす。
- `at`: その地点を含む建物と、点群で作った上の段すべてに適用（地点を並べると、重なった建物データをまとめて 1 つの外観にする）。`rename`: 地図の建物名を置き換える
- `set`: 建物本体の値を変える。`minH` を入れると高架になり（線路をまたぐ駅舎）、壁の柄はその床から数える
- `look.floors`: 地面からの階ごとの壁の柄。`shop`（柱の間にガラスの店、上にアクセント色の帯）、`panel`（白いパネルにアクセント色の縦の帯。階ごとに半ベイずらす千鳥）、`parking`（腰壁の上が暗い開口とルーバー）、`ribbon`（横に続く窓の帯）、`screen`（アクセント色の壁に白い縦棒を互い違いに並べた目隠し。8 ベイに 2 ベイは白い壁にアクセント色の縦帯とルーバー）、`fins`（白い太い縦のフィンが 3 m ごと、間に細い縦長の窓と灰色の腰パネル）、`curtain` / `curtain2`（2 層続くガラスの壁の下の階＝下に白い腰壁／上の階＝上に張り出した庇の帯）、`terrace`（奥まった `accent2` 色の壁に大きなガラス戸）、`maroon`（`accent2` 色の 1 階）、`slits`（白いパネルに細い縦のスリット）、`slats` / `slats2`（駐車場の白い縦格子。暗い開口の前、5 本に 1 本はアクセント色／灰色の壁）、`grid`（ガラスの格子）、`store2`（2 階の明るい売り場のガラス面）、`base`（白い壁にところどころ店の入口）、`market`（スーパーの店先: 上にクリーム色のパラペット、その下に `accent` 色の庇、庇の下はガラスの店先と腰壁。マルエツ）、`tenants`（色の四角に店名の看板。`look.tenants` に `{"階": [[文字, 地の色, 文字の色], 2 つ]}`）、`plain`（窓なし）。テクスチャには、その外観が使う柄の段だけを並べる
- `look.faces`: 東西南北の面ごとの `floors`（`{"n": {"floors": [...]}}`。壁の外向きで決める）
- `look.zones`: 面の途中で柄を変える区間。`from`〜`to` の線から `w` m 以内の壁をその `floors` にする。`align: true` で、外から見て区間の左端から柄を 1 回だけ貼る（`tenants` の看板用。階 k はベイ k）
- `look.relief`: 立体の飾り。`fins`（柄が `fins` の階に、柄の柱と同じ位置へ張り出す縦の柱 `{w, d}`）、`eaves`（`[{floor, depth, h, color, faces, rail}]` = その階の上端に張り出す庇・床。`rail` で先端にガラスの手すり）
- `fill_gaps: true`: 点群で作った段の間のすき間（格子越しに中を写した所など）を、下の段の上端まで埋める
- `look` を省くと、壁の柄は付けず、`color`（壁の色）と `set`・`fill_gaps`・`rename` だけを設定する（写真が少なく、色と形だけ直せるとき。ライオンズステージ戸塚ルヴェールの丘）。`set.balcony_tiers: true` を付けると、ベランダを段（点群で作った上の段）の輪郭にも、その段の高さの範囲で付ける（段の高さは建物全体の高さ ÷ 階数。ふつうのベランダは本体の輪郭だけ）。`props.json` の `balconies` の `k0` = その段の最初の階。それより上は窓のない壁
- `look.wall` / `accent`: 壁とアクセントの色。`floor_h`: 1 階分の高さ。`glass_floors`: 入口まわりをガラス面にする階数、`door_w`: その左右の幅（既定 7 m）、`door_kind`: `open` にするとガラスではなく開いた通路
- 入口は、建物の壁に届いている高架の歩道（デッキ）の端から自動で決める（`entrances` に `[x, z]` を書けば追加できる）
- `look.sign`: 壁面の大きな看板（文字だけ。実物のロゴではない）。東西南北それぞれいちばん長い壁の中央に 1 枚（`min_len` 壁の長さの下限、`max_w` 幅の上限、`ratio` 縦横比。配置は `build_props.py` → `props.json` の `bigSigns`）
- 適用は `python tools/landmarks.py`（`--undo` で戻す。何度実行しても同じ結果）。`build_city.py` と `lidar_shape.py` も最後に同じ処理を呼ぶ。`city.json` には建物の `look` と、外観の中身 `looks` が入る
- 現在はトツカーナ（戸塚駅西口。地上 7 階、駅側の 2〜3 階はガラス面、4〜7 階はこげ茶の壁に白い縦棒の目隠し、屋上は駐車場）と、戸塚駅（線路をまたぐ橋上駅舎。床は線路から約 5 m、入口は開いた通路、緑の JR と白地の駅名の看板）。公開写真（Wikimedia Commons）を見て合わせたが、写真の無い面と窓の細かい位置は推定
- 戸塚区総合庁舎（区役所。地上 9 階、`floor_h` 4.78 m）も、路上写真（持ち主提供、東側の道路から）と Wikimedia Commons の写真（北東の角から）を見て同じ仕組みで設定した: 東の面は 1 階が店のガラス面と青い庇、2〜3 階は 2 層のガラスの壁、その上に張り出した庇、4 階から上は白い縦のフィン（立体）。北の面は白いパネルにスリット、2〜3 階はえんじ色の壁の前にガラスの手すりのテラス 2 段。写真の無い西・南の面は東と同じ柄（推定）。看板「戸塚区役所」は 2 階のガラスの高さ
- サクラス戸塚（`floor_h` 4.0 m）は、ja.wikipedia と Commons の写真 2 枚を見て、南の面を区間（`zones`）で分けた: 東の角の塔（ガラスの格子・テナント看板 2×4 枚）、波形の白い縦格子（桜色の板混じり）、Saclass の文字の白い塔、西の端の灰色の駐車場（1 階は吹きさらし・2 階はテラス）。東・北・西の面は灰色の駐車場の柄（推定）。点群の段のすき間（13.5〜17 m）は `fill_gaps` で埋めた
- `look.sign` は並べて複数書ける。`at` を入れると、その地点にいちばん近い壁（看板の高さに壁がある段から選ぶ）に 1 枚、`w` で幅を指定
- グランシティの付属棟（道路側。クリーム色の壁・濃い茶の縁・シャッター 2 枚。`door_kind: "shutter"` と `door_off`＝入口の壁からの許容距離）と立体駐車場（`louver`＝灰緑のパネルと暗い開口の 3 層）も、路上写真（持ち主提供）を見て同じ仕組みで設定した。エントランス棟は、道路から最初に見える「時計の棟」（`gate.clockhouse`、`tools/clockhouse.py`）。2026-11 に作り直した: 位置と大きさは点群の高さから測った（正面の幅 15 m・奥行き 7 m・軒 5 m・マンサード屋根の上端 7 m・時計の部分 約 9 m、後ろに奥行き 4 m・高さ 4.4 m の平屋。前は道路ぎわまで約 5.5 m の車寄せ、右に高さ約 3.6 m の低い棟 `walls`。以前は写真からの推定で約 14 m ずれていた）。外観は不動産サイトの公開写真（三井のリハウス・ノムコム）を見て書き起こした（`detail/clockhouse.js`）: クリーム色の壁に白い付け柱、アーチ窓 4 つと中央の赤い枠のガラス扉、扇形の黒いガラスの庇、壁灯、軒の蛇腹、紺灰色のスレートのマンサード屋根に黄土色の枠の丸窓のドーマー（前後 4 つ・横 1 つ）、正面中央に黄土色の丸い枠の時計。中庭側の平屋もアーチ窓と赤い扉、屋上に白い手すり。その先の噴水の向こうに、独立したアーチの門（`gate.arch`: `s` = 基準点から奥への距離、`w` 幅、`open` 開口の幅、`h` 高さ）。壁の箱は窓の柄なし（`plain`）で、外観は壁の前に張った板と立体の飾り。中央の扉と中庭側の扉は開け閉めできる（`public/src/doors.js`。近くで **F**、スマホは近づくと出る「開ける」ボタン。キャラが扉の方を向いて両手で押す動き（上半身だけ。0.9 秒。歩き・走りは止めない。`character.js` の `doorPose`、`player.js` の `startDoor`）をし、手が届くころ（0.3 秒後）に赤い枠のガラス扉 2 枚が内側へ開き、閉じている間は通れない。離れて 4 秒で自動で閉まる。扉の間に人がいる間は閉まらない。形は `clockhouse.js` が作って `DOORS` に登録し、当たり判定は `world.addDoor()`。確認は `node tools/dev/doorcheck.js <出力フォルダ>`）。

### スタート地点
`tools/config.py` の `START`（緯度経度）と `face_toward`（向く先の緯度経度）。現在はグランシティ パレ・ド・リヴァージュ西側の道路上、門の正面でマンション側を向く。

### 現地情報による修正
`data/corrections.json` に、元データと現地が違う箇所を書く。`build_city.py` 実行時に反映。ゲーム内の修正モード（E）から保存すると自動で追記・再生成される（`start.bat` = `tools/server.py` で起動したときのみ）。
- `remove_buildings`: `{"at": [x, z]}`（その地点を含む建物を削除。データ源が変わっても有効）または `{"id": ...}`
- `set_height`: `{"id" または "at", "h"}`
- `add_buildings`: `{"id", "outer": [[x, z], ...], "h"}`
- 修正モードの「前回の保存を取り消す」で、最後に保存した分だけ戻せる
- ファイルを削除して `build_city.py` を再実行すれば元データに戻る

### 目的地
`tools/config.py` の `WAYPOINTS` に名前と緯度経度を追加 → `build_city.py` を再実行。
光の柱・ミニマップのマーカー・距離表示が出る。目的地が建物の中の場合は、その建物の外壁に着いた時点で「到着」になる。

- `tools/dev/shot.js`: ゲームをヘッドレスブラウザで起動し、指定した視点のスクリーンショットを撮る（修正前後の見比べ用。使い方はファイル先頭のコメント、視点の例は `tools/dev/views.example.json`）
- `tools/dev/evalroof.py`: 屋根の形の確かさを数字で測る（モデルの屋根の高さと点群の高さの誤差）
- `tools/dev/touchshot.js`: タッチ操作の確認。スマホの画面サイズのヘッドレスブラウザに指の動きを疑似的に送り、キャラ・カメラ・地図の反応を数字と画像で出す（使い方は先頭のコメント。全体で 10 分ほど）
- `tools/dev/speedcheck.js`: 描画が遅くてもキャラの速さが実時間で落ちないことの確認（進んだ距離 ÷ 実際の時間。`--old` で以前の計算と比べる）
- `tools/dev/mpcheck.js`: マルチプレイの確認。手元のサーバー（`server/local.js`）とヘッドレスブラウザ 2 つで、お互いが見える・動きが伝わる・戦闘オン同士だけ当たる・倒れて復活する、を数字で確かめて画面を撮る（先に `cd server && npm install`。約 5 分）
- `tools/dev/memcheck.js`: メモリの内訳（メッシュごとの頂点データ・模様の大きさ・JS のヒープ）を出す。`node tools/dev/memcheck.js "?touch"` でスマホの設定、引数なしで PC の設定
- `tools/dev/charview.html`: キャラだけを 4 方向（正面・真後ろ・斜め後ろ・手元）から見るページ。街を読み込まないのですぐ開く。リポジトリの直下を配信して開く（`python -m http.server 8772 --bind 127.0.0.1` → `http://127.0.0.1:8772/tools/dev/charview.html?pose=5.5&live`）。`pose` は速さ（0 立ち / 1.6 歩き / 5.5 走り）、`face` を付けると手元の代わりに顔のアップ。詳しくはファイル先頭のコメント。ヘッドレスで撮るのは `tools/dev/charshot.js`（使い方は先頭のコメント）
- ゲーム本体の撮影用: `?shot&pose=5.5` で、その場で走りの姿勢になる
- `tools/dev/walkcheck.js`: 歩道橋・デッキ・階段を歩いて通れるかを、ゲームの当たり判定で調べる（中心線を 0.25 m ごとにたどり、0.4 m を超える段差と、手すり・建物に体が重なる所を通路ごとに数える）。`node tools/dev/walkcheck.js`
- 作業の進め方とクラウド環境での注意点は `CLAUDE.md`
